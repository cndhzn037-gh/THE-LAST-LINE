## 一、22000 行都是有效内容吗？

### 1.1 实测数据

| 指标 | 数值 |
|---|---|
| 运行时 JS 文件 | 55 个（另有 sw.js） |
| 总行数 | 22,338 |
| 空行 | 1,257 |
| 注释行 | 571（仅 2.6%） |

| UI 外壳 | 3,907 | 17.5% | 主菜单 840 / 俯视选角 746 / 存档转移 726 / 输入 720 / 其他 |
| 第二种模式 | 4,769 | 21.4% | 俯视射击 3k+、操控模式 819 |
| 模拟 | 2,970 | 13.3% | 人类 AI、丧尸 AI、战斗、状态、分离、守卫 |
| 世界 | 1,617 | 7.2% | 网格、流场、寻路、分析、拼接 |
| 渲染 | 1,301 | 5.8% | 相机、地形、HUD |
| 数据 | 1,526 | 6.8% | 单位模板、地图、波次、地砖 |
| 核心 | 568 | 2.5% | 配置、状态、工具 |

（另有 21 个测试文件、5,069 行，不计入 22.3k。）

### 1.2 和我们的对比

- 我们：16,260 行，其中代码 14,367 行、注释 1,763 行。
- 他们：22,338 行，其中代码 20,510 行、注释 571 行。
- 把他们的"编辑器 + UI 外壳 + 第二种模式"（14,356 行）拿掉，引擎部分约 **8,000 行**；
  我们的 14,367 行里同时包含引擎、内容、UI、地图编辑器。
- 所以：**不是我们的工程小，而是他们多了"产品面"**——三个编辑器、一个第二游戏模式、一整套菜单/设置/存档转移/触控适配套件。

**可复用的判断**：不要用行数衡量工程；用"功能面"和"每个功能面的完成度"衡量。

## 二、UI 规划与手机触控（最值得学）

### 2.1 统一主题与控件

`js/ui/style.js`：

- `THEME`：面板/边框/文字/弱化/六个语义色/圆角，全部文件共用一套。
- `uiButton(ctx, rect, label, {variant, selected, disabled, align, fontSize})`：
  `primary / success / danger / warning / ghost / dark` 六种语义；
  统一圆角、描边、顶部高光、禁用透明度。
- `uiToggle`：开关的轨道 + 圆钮，选中/未选两个状态。
- 结果：**所有界面看起来是一个游戏**，而不是每个面板各写一套。

我们有大量 DOM + Canvas 混合 UI；建议先抽一套"语义控件"（主/次/危险/成功/幽灵），
所有新面板只允许用这套，不再手写颜色。

### 2.2 命中区：先收集，再统一扩张

- 每个界面绘制时把自己的可点区域 push 进 `st.xxxHitboxes`；
- `gatherHitboxes()` 按层级把所有数组拼起来；
- `hitAt(x,y)` 从最上层往下找，天然支持"弹层盖住底层"；
- `expandTouchTargets()`：触屏时把所有命中区**扩到至少 40 CSS px**（`TOUCH_MIN_CSS = 40`），
  最多外扩 14px（`TOUCH_PAD_CSS = 14`），并且**避开相邻命中区**，不互相覆盖；
- 视觉尺寸不变，只放大可点范围；容器卡片不算邻居，避免永远扩不动。

这就是他们手机手感好的核心：**视觉可以小，手指必须够得着**。
我们的 Canvas 按钮目前是"画多大点多大"，手机上必然难点。

### 2.3 反馈与过渡

- `toast`：最多 3 条、同文案只刷新时间、2.6 秒淡出、超宽省略号。
- `transition`：切界面先黑场 0.22 秒再淡入；弹层用三次方缓动淡入；切界面清空按压状态。
- 列表拖动滚动、滑条步进、长按判定都有统一工具（`input.js`：`dragThreshold=9/uiScale`）。

### 2.4 编辑器布局

- 左侧列表、右侧分区表单、底部固定操作栏（保存/取消）。
- 特殊机制选中后，专属字段自动上移并滚到可见（不会"要翻很久才找到"）。
- 字段按阵营/机制隐藏无关项，减少视觉噪音。
- 顶部实机演示区，改参数立刻看到效果。

### 2.5 我们的差距

- 入口层级深、命名偏内部术语、帮助是长文；
- 控件样式不统一，颜色散落在各处；
- 没有"触控目标"概念，Canvas 小按钮在手机上很难点；
- 没有首次引导的分步高亮。

**结论**：UI 是 2.1 的主战场，优先级仅次于 2.0 的基础功能。

## 三、地图编辑器与地块（2.4 的参考）

### 3.1 他们已有的

- 画笔/画线/方框/矩形/填充/右键擦除；Esc 退出工具；拖到边缘自动平移。
- 地图缩放上限随尺寸提高（单图 5×、2×2 10×、4×4 21×、最大 40×）。
- 坐标尺、中心轴、十字定位线、坐标读数。
- 撤销栈：快照式，40 步（`mapEditorPushUndo` / `mapEditorUndo`）。
- 地块：内置 + 自定义；颜色/花纹/边缘/透明度/通行/子弹穿透/减速/秒伤/可破坏/结构血量；
  相连同类共用一个结构血量，打碎整组消失；花纹按世界坐标连续，不随格子断开。
- 实体块单独编辑；地图 schema 版本 + 旧档迁移。

### 3.2 他们没有、我们可以超车的

- **网格/顶点吸附**：他们只有整格落笔，没有"自由/半格/端点吸附"开关，也没有 AutoCAD 式捕捉提示。
- **长度/角度实时读数**：画矩形时没有尺寸标注。
- **吸附优先级与冲突处理**：端点 > 边 > 格心；按住 Alt 临时关闭吸附。

这些正好是用户明确要的，2.4 做成"我们的特色"，不是补课。

### 3.3 地块系统对我们的意义

我们现在的障碍是矩形 + 少量地形类型；要做"每个方块单独贴图 + 功能"，
建议数据模型：

```
TileDef {
  id, name, category,        // 地面/墙体/危险/特殊
  color, pattern, patternColor, edgeColor, alpha,
  passable: { human, zombie }, bulletBlock,
  slowPct, dps, breakable, hp,
  render(ctx, x, y, size, worldSeed)  // 花纹按世界坐标连续
}
```

地图层：`terrain[]`（功能）+ `tiles[]`（外观/属性），二者可分离，便于"换皮不换功能"。

## 四、重置功能：他们怎么做对的

`js/data/units.js`：

- `BUILTIN_ORIGINAL`：启动时对内置单位做**深拷贝并冻结**，之后永不修改。
- `resetUnitToDefault(u)`：
  1. 先删掉编辑器后来加上、但原始对象没有的字段（special/heal/dash…）；
  2. 再把原始对象的每个字段逐个写回；
  3. `_modified = false`；
  4. `normalizeUnit(u)` 按 `UNIT_LIMITS` 再夹一次；
  5. 存盘。
- 自定义单位没有"默认值"，所以只对内置单位显示"还原默认"。

**我们上次为什么坏**（推断，待代码复核）：
- 基线可能是"当前值的一份引用"，改字段时把基线一起改了；
- 或者重置只覆盖了一部分字段，新加的字段/机制残留；
- 或者没有 normalize，某些值回到越界状态。

**2.2 的硬性设计**：
- `BASE_UNIT` 用 `JSON.parse(JSON.stringify(...))` 深拷贝 + `Object.freeze`；
- 重置 = 删除多余键 → 逐键写回 → normalize → 存盘；
- 分区重置只允许白名单键集合；
- 重置前压一次撤销快照；
- 测试：把字段全改成极端值 → 重置 → `deepEqual(unit, BASE_UNIT)`。

## 五、AI 装填/过热：可以安全接入的部分

他们的做法（`ai-human.js`）：

- 没目标 → 换弹；
- 低压力（最近丧尸 >120 且压力权重 <2）+ 距离 >130 + 弹匣 <40% + 250px 内同兵种没在换弹 → 换弹；
- 过热：压力低时 65% 开始降温，20% 才恢复射击；压力高时允许打到过热；
- 目标粘性：旧目标仍活着且在射程/视线内就继续打（人类）；丧尸旧目标在 1.5 倍距离内不换。

**接入原则**（用户强调过：每个兵种有自己的寻路/AI 节奏）：
- 只改"何时开始换弹/降温"，不改移动、索敌、寻路；
- 每个兵种一个开关与阈值，默认只对步枪/机枪/狙击/盾兵/磁爆生效；
- 激光/喷火/液氮保持各自节奏，先不动；
- 所有新逻辑加断言，跑完整 selftest + newunits。

## 六、地形生成（2.6 的参考）

`js/modes/topdown/world.js`：

- `seededRandom(seed, cx, cy)`：每个区块独立种子，同种子可复现。
- 每区块 2~5 个障碍簇（墙/掩体/障碍）+ 1~3 个房屋；
- 房屋 8~13 格，2~3 个门，门尽量分布在不同边；
- 冲突检测（房屋与已有障碍重叠 >30% 就跳过）；
- 区块加载半径 + 局部流场。

**不足**：只有"散块 + 房屋"，没有主题、没有任务目标、没有难度曲线。
我们要做的是"可玩地形"：房间-走廊/BSP + 预制件 + 连通性校验 + 功能布置（出生/据点/资源/刷怪/Boss）+ 主题与难度预算。

## 七、其他发现（不全是优点）

| 发现 | 说明 | 对我们的意义 |
|---|---|---|
| 没有音频 | 全项目没有 `AudioContext`，`OB.sfx` 全是可选调用 | 我们的音效是优势，别丢 |
| 注释极少 | 只 2.6% 注释，且 `ai-human.js` 有 16 行双重编码乱码 | 我们的注释密度是优势，但别学乱码 |
| 非确定性模拟 | `Math.random` + 可变 dt | 我们固定步长 + mulberry32 更强 |
| 无自动存档 | 只有手动/导出，没有定时自动存档 | 我们的 15 秒自动存档是优势 |
| 全局命名空间 | 55 个文件挂 `OB`，每文件重复 import 20 个常量 | 单文件分节更适合我们 |
| 存档分散 | 配置/单位/地图/波次/地砖各自 key | 我们单份存档更稳 |
| 触控 | 40px 命中区 + 防重叠扩张 + 长按 + 列表拖动 | **必学** |
| 过渡 | 黑场 0.22s + 弹层缓动 | 可学，成本低 |

## 九、相机热点追逐（已决定不做）

**是什么**：镜头不是死跟玩家/固定中心，而是记录最近几秒"哪里在打仗"——
枪口火光、命中、爆炸——在镜头目标点上按权重混入这些热点，2.6 秒后衰减。
效果是"镜头会自然偏向交火处"，但不抢玩家控制。

**最终决定（2026-11-07）**：不做。我们的镜头是玩家手动拖动/跟玩家，方向和热点追逐不一致；
加入会抢镜、干扰操作。决策见 ADR-010，节点 I-01~I-04 标 dropped。

## 六、2.9 剩余优点逐条评估

> 结论先行：能吸收的已经吸收，剩下的要么与我们的单文件架构冲突，要么收益低于维护成本。

### 6.1 已吸收

| 点 | 我们的落地 |
|---|---|
| 触控目标 ≥ 40px | 全局 44px，含菜单、市场、编辑器、字段重置 |
| 语义化控件 | 现有终端 CSS 变量统一主色/危险/弱化；未抽组件，但颜色不再散落 |
| 界面过渡 | 进入战场黑场淡入；减少动态效果可关闭 |
| 地块纹理 | 纯色/斜纹/网格，按范围裁剪 |
| 地块合并血量 | 相邻同色同纹理自动成组，整组扣血/移除 |
| 难度预算 | 生成难度三档，控制建筑、掩体、深度与刷怪 |
| 性能预算 | FPS/模拟/渲染耗时读数 + 270 单位压力脚本 |
| 存档转移 | 存档码复制/分享/导入；旧档缺字段兜底 |

### 6.2 评估后不做

| 点 | 不做的原因 |
|---|---|
| 第二套俯视射击模式 | 与“自动作战沙盘”的核心定位冲突，工程量等于再做半个游戏 |
| 三编辑器并列（单位/波次/地砖） | 我们已把单位、地图、地形生成收进一个工作台；再拆会回到入口迷路 |
| Canvas 命中区统一收集/扩张 | 现有交互基本迁到 DOM；剩余画布点击是大目标，收益低 |
| 地图 40× 缩放 | 我们的地图尺寸与镜头范围固定，超高缩放没有使用场景 |
| 编辑器左侧列表 + 右侧表单 | 当前单列分区在 844×390 更稳；左右栏在窄屏会挤压 |

### 6.3 仍可做但未做

- 画布内小按钮的命中区扩张（目前主要是大目标）
- 编辑器左右栏宽屏布局（窄屏仍单列）
- 地块边缘羽化/相邻自动拼接

### 6.4 结论

2.9 的“逐条评估”到此完成。剩余项均为可选优化，不阻塞 2.x 验收。
